Miracle Cloud VM is a Linux command-line project for managing virtual machines with QEMU-based tooling. The repository includes the main manager.sh script and editvm.sh, a configuration editor that can rebuild a VM from its configured cloud image.

[!IMPORTANT]
This README documents the scripts currently included in this repository. Actual capabilities depend on the version of manager.sh and the VM configuration files present on your server. Test on a non-production VM before relying on it.

✨ Features
Main manager (manager.sh)
The main script is the primary entry point for the project's VM workflow. Consult its menu and source code for the exact operations supported by the version you install.

VM editor (editvm.sh)
The editor is designed for VM configuration files in the format generated by the manager. It can prompt for these settings before rebuilding the selected VM:

Hostname
Guest username and login password
RAM allocation in MB
Virtual CPU core count
QEMU CPU profile (including a host CPU profile that requires KVM)
Virtual disk size (disk shrinking is rejected by the script)
SSH host port
Host-to-guest port forwards
GUI mode flag
Guest OS image URL from the existing VM configuration
The editor validates several inputs, checks that the VM does not appear to be running, stages replacement files, and keeps timestamped copies of the previous disk, seed ISO, and configuration when those files exist and enough storage is available.

[!WARNING]
Editing performs a guest OS rebuild. The new disk is created from the configured cloud image. Existing applications and files on the old guest disk will not be part of the new disk. Do not use this operation as a routine, non-destructive settings edit.

🧩 Requirements
A supported Ubuntu or Debian system with APT.
Root privileges or sudo for installation and VM disk/configuration operations.
QEMU x86 system emulator and qemu-img.
cloud-localds from cloud-image-utils.
wget, openssl, awk, sed, find, sort, procps, and standard Linux utilities.
Sufficient free disk space for a fresh guest disk and a backup copy of the existing disk.
A valid, reachable cloud image URL stored as IMG_URL in the VM's .conf file.
A VM directory containing the .conf files produced by the compatible manager.sh version.
KVM access for host CPU passthrough or accelerated virtualization. CPU passthrough may not work on VPS/container providers that do not expose KVM.
Install the common packages:

sudo apt update && sudo apt install -y \
  qemu-system-x86 qemu-utils cloud-image-utils \
  wget curl openssl ca-certificates \
  ncurses-bin coreutils util-linux procps \
  iproute2 awk sed findutils
The scripts may require additional packages depending on the features enabled in your version.

Clone the repository if Git is installed:

git clone https://github.com/cryzenn244-png/Miracle-Cloud-Vm.git
cd Miracle-Cloud-Vm
Install the dependencies listed above, then inspect the scripts:

less manager.sh
less editvm.sh
Check shell syntax before executing:

bash -n manager.sh
bash -n editvm.sh
If both commands return no output and exit successfully, the shell syntax check passed. This does not guarantee that VM creation or rebuild will succeed on a particular host.

🧰 Editing and rebuilding a VM
1. Stop the VM first
Use the main manager to shut down the selected VM cleanly. The editor attempts to detect a running QEMU process associated with the VM disk, but this check is not a substitute for confirming the VM is stopped.

2. Check the VM directory
By default, editvm.sh searches for *.conf files in $HOME/vms. Because sudo can change the effective home directory, the default may be /root/vms when run with sudo.

If the manager stores VMs elsewhere, specify the actual directory explicitly:

sudo env VM_DIR=/path/to/vms /usr/local/bin/editvm.sh
Replace /path/to/vms with the real directory containing the manager's VM configuration files. Do not guess this path. The editor expects files such as NAME.conf, NAME.img, and NAME-seed.iso in that directory, following the current script's naming convention.

3. Launch the editor
sudo /usr/local/bin/editvm.sh
Choose the VM by its displayed number. The script reads the selected .conf file and displays its current settings.

4. Enter the new settings
Press Enter to keep an existing value where the prompt supports it. Supply valid values for the fields you want to change:

Setting	Expected input
Hostname	Letters, digits, underscore or hyphen; maximum 63 characters in the current script
Username	Lowercase Linux username format
RAM	Positive integer in MB, for example 4096
vCPU cores	Positive integer, for example 4
Disk	Size such as 30G or 512M; shrinking is blocked by the current script
CPU profile	Select one of the profiles displayed by the editor
SSH host port	Integer from 23 to 65535
Port forwarding	Comma-separated host:guest pairs, for example 2222:22,8080:80
GUI mode	y or n
Password	Enter a new password at the hidden prompt, or leave blank to retain the current one
The requested RAM and vCPU values must also fit within the host's actual capacity. The current editor validates that values are positive, but does not perform a complete host-capacity reservation check.

5. Confirm the rebuild
Read the summary and warnings carefully. The editor requires you to type the exact word REINSTALL to proceed. Any other response cancels the operation.

The current script downloads the configured image, converts it to QCOW2, resizes the new virtual disk, creates a cloud-init seed ISO, and then saves backups before replacing the current disk and configuration files.

6. Start and verify the VM
Start the VM using the main manager. First boot may take several minutes while cloud-init configures the guest. Verify console access, hostname, login credentials, SSH access, networking, and disk size before relying on the rebuilt VM.

[!NOTE]
CPU profile names and model strings are requests passed through the manager's configuration. Actual CPU features depend on the installed QEMU version, host CPU, and whether KVM is available. A profile name does not make a host processor physically become a different model.

📁 Configuration and storage
The editor currently expects these files in the selected VM directory:

vms/
├── VM_NAME.conf        # Manager-generated shell key/value configuration
├── VM_NAME.img         # Current VM disk image
└── VM_NAME-seed.iso    # Cloud-init seed image
The .conf file must include a non-empty IMG_URL pointing to a compatible cloud image. The editor uses variables such as VM_NAME, OS_TYPE, CODENAME, HOSTNAME, USERNAME, PASSWORD, DISK_SIZE, MEMORY, CPUS, SSH_PORT, CPU_MODEL, and CPU_FLAGS.

Only use configuration files you trust. The current editor sources the selected .conf as a shell file, so a modified or untrusted configuration file could execute commands with the editor's privileges.

The current editor also assumes the disk and seed filenames match its naming convention. If your installed manager uses a different format or storage layout, adapt and test the scripts before using the editor.

🛡️ Backups and data safety
Stop the VM before editing it.
Back up important guest data independently before a rebuild.
Ensure sufficient free storage for the downloaded image, new disk, and backup of the old disk.
Keep the original .conf, disk image, and seed ISO until the new VM has been verified.
Never shrink a disk image through this editor; the script rejects requested sizes below the detected current virtual size.
Treat backups as sensitive because old disks and configuration files may contain private data or credentials.
Test restore procedures. A backup file existing on disk does not guarantee that it can be restored successfully.
The editor's backups use timestamped suffixes such as .pre-reinstall-YYYYMMDD-HHMMSS. Backup copies can consume substantial disk space.

🧯 Troubleshooting
<details> <summary><strong>“VM directory not found” or “No VM .conf files found”</strong></summary>
Find the actual VM directory used by your manager, then run:

sudo env VM_DIR=/actual/path/to/vms /usr/local/bin/editvm.sh
The directory must contain the expected manager-generated .conf files. Use the real path from your installation.

</details><details> <summary><strong>“Missing dependency”</strong></summary>
Install the common dependencies:

sudo apt update && sudo apt install -y qemu-utils cloud-image-utils wget openssl coreutils util-linux procps
Check that required commands are available:

command -v qemu-img cloud-localds wget openssl awk sed find sort
</details><details> <summary><strong>“IMG_URL is empty” or image download fails</strong></summary>
Inspect the VM's .conf file and verify that IMG_URL points to a trusted, reachable, compatible cloud image. The editor cannot rebuild a VM if the image source is missing or inaccessible.

</details><details> <summary><strong>QEMU/KVM or host CPU profile does not work</strong></summary>
Check the QEMU version and whether virtualization flags are exposed:

qemu-system-x86_64 --version
grep -Eoc 'vmx|svm' /proc/cpuinfo
ls -l /dev/kvm 2>/dev/null || true
A positive CPU flag count alone does not guarantee KVM access. A VPS provider or outer hypervisor may need to expose nested virtualization and /dev/kvm. Use only CPU profiles supported by your QEMU version and host.

</details><details> <summary><strong>Guest does not accept the new password or hostname</strong></summary>
Cloud-init support and behavior depend on the selected guest image. Confirm that the image supports cloud-init, allow its first boot to complete, and inspect the VM console and guest cloud-init logs. Do not assume every generic OS image will apply cloud-init configuration.

</details><details> <summary><strong>Rebuild fails or disk space is low</strong></summary>
Check free space before retrying:

df -h
Keep the original disk and backups until you understand the failure. Do not manually delete backup files unless you have confirmed they are no longer needed.

</details>
🔐 Security recommendations
Download scripts only from a repository and branch you trust.
Inspect shell scripts before running them as root.
Use strong guest passwords and protect VM configuration files.
Restrict SSH and forwarded ports with firewall rules.
Do not expose QEMU monitor sockets or administrative interfaces publicly.
Keep host packages and guest operating systems updated.
Store backups securely and restrict access to them.
